- 2026-10-04 · turbo dev pipeline · `pnpm dev` crashed apps/server immediately (`ERR_MODULE_NOT_FOUND` for `@worksheet-clone/shared/dist/index.js`) because the `dev` task in `turbo.json` had no `dependsOn: ["^build"]`, so `tsx watch` started before `packages/shared` had ever been built → assumed dev mode wouldn't need a build step since `tsx`/`vite` compile TS on the fly, forgot that workspace _dependencies_ consumed via `node_modules` package.json `main`/`types` still need their own dist to exist → whenever a workspace package switches from source-pointing to build-output-pointing `main`/`types` (see the packaging entry below), immediately check the `dev` task too, not just `build`/`test`/`typecheck`.
- 2026-10-04 · docker/turbo · `apps/server#build` (plain `tsc -p`) failed to find `@worksheet-clone/shared`'s compiled types in a clean GitHub Actions Docker build even though turbo's task graph correctly orders `shared#build` before it → `tsc -p` doesn't use TS project references, so a dependency's build finishing isn't itself a guarantee visible to it in every environment; not reproduced in two local fresh-clone/simulated-Docker-layer runs, so suspect something cold-cache/timing-specific to that runner → when "cannot find module" for a workspace package shows up only in CI/Docker, treat it as possibly build-order/caching related even if the turbo dependency graph looks correct on `--dry=json`; converting the consumer to `tsc -b` too (not just the dependency) is the stronger fix to try first. (left unresolved — deprioritized, Docker isn't installed locally to keep debugging against)
- 2026-10-04 · packages/shared build · `tsc -p tsconfig.build.json` on a `composite: true` project silently emitted zero files and exited 0, no error → composite projects need build-mode (`tsc -b`) to actually emit via a project-reference-aware build; plain `-p` mode no-ops without diagnostics on at least this config → whenever a package sets `composite: true`, always build it with `tsc -b`, never plain `tsc -p`, and verify emitted files explicitly (`find dist`) after any build-step change — don't trust a zero exit code alone.
- 2026-10-04 · packages/shared packaging · pointed `main`/`types` at `./src/index.ts` (raw TS) so `apps/server`'s compiled `dist/main.js` crashed at runtime with `ERR_MODULE_NOT_FOUND` under plain `node` (vitest/tsx tolerate extensionless/TS imports; plain Node ESM does not) → assumed a source-pointing workspace package would "just work" everywhere because it worked under the test runner → for any workspace package consumed by code that runs as compiled JS in production, give it its own build step and point `main`/`types` at the build output, then verify by literally running `node dist/main.js` standalone, not just `vitest`/`tsc --noEmit`.
- 2026-10-04 · apps/web tooling · pinned `vite: ^6.0.0` directly while `vitest@2.1` only supports Vite 5 as a peer, producing two parallel Vite installs and a `tsc` type-identity clash on `vite.config.ts` (TS2769, "Plugin<any> is not assignable to PluginOption") → didn't check vitest's peer range before picking a vite version → when adding `vite` (or anything with a vitest/plugin peer dependency) to a package that also uses vitest, run `pnpm why vite` for duplicate versions before debugging the resulting type errors as if they were a real config bug.
