- 2026-11-07 · server error responses · M1 shipped without a Fastify `setErrorHandler`, so any unexpected exception returned Fastify's default 500 body including the raw `error.message` (e.g. a Drizzle/Postgres query failure text) to the client, and rate-limit/malformed-JSON/unknown-route errors used Fastify's `{statusCode, error, message}` shape instead of our `{ error: { code, message } }` convention — not caught because every test only exercised the domain-error paths the routes handled by hand → hand-written try/catch per route covers only the errors you anticipate; the framework's defaults cover the rest, silently → added one global error handler (DomainError → its code, 429 → RATE_LIMITED, other 4xx → VALIDATION_ERROR, everything else → logged + generic INTERNAL_ERROR) and an `/api` not-found handler in every environment, with tests for each non-domain path; next time, when adopting a response-shape convention, add a test that probes the framework's own error paths (bad JSON, unknown route, thrown Error, plugin errors), not just your own.

- 2026-10-04 · RTK Query + vitest jsdom · testing `HomePage` (which calls RTK Query's `useMeQuery`) by mounting it with a real store and `vi.stubGlobal("fetch", ...)` crashed with `TypeError: RequestInit: Expected signal ("AbortSignal {}") to be an instance of AbortSignal` from Node's built-in fetch/undici → `fetchBaseQuery` builds its own `AbortController` internally, but under Vitest's jsdom environment `AbortController`/`AbortSignal` are jsdom's own polyfill classes, not Node's; undici's `new Request(url, { signal })` rejects a jsdom-realm `AbortSignal` even though both are named `AbortSignal` → stubbing `fetch` doesn't avoid this since the crash happens inside `fetchBaseQuery` building the `Request` object before `fetchFn` is even called → fixed by not exercising the real RTK Query network stack in this component test at all: `vi.mock` the `authApi` module's hooks (`useMeQuery`/`useLogoutMutation`) directly instead of mocking `fetch`, which is also more in keeping with CLAUDE.md's testing split (component tests vs. Playwright for real flows) → whenever a component test needs to render something that calls an RTK-Query (or any fetchBaseQuery-based) hook under jsdom, mock the hook module, not `fetch` — jsdom's `AbortController` is not interchangeable with Node's for this purpose.
- 2026-10-04 · server test cleanup (shared local Postgres) · three test files (`domain/auth.test.ts`, `test/functional/session.test.ts`, `test/functional/auth.test.ts`) each ran against the same local docker-compose Postgres and cleaned up in `afterEach` with an unscoped `delete from sessions` plus a `delete from users where email like 'test-...'`; when vitest ran them concurrently, `domain/auth.test.ts`'s pattern (`test-%@example.com`) also matched `test-auth-...@example.com` rows from a different file, and the unscoped `delete from sessions` wiped every file's in-flight sessions — one run hit a real foreign-key violation (`insert into sessions ... violates foreign key constraint`) because another file's cleanup deleted the user mid-test → assumed per-file test isolation without checking that cleanup patterns across files don't overlap, and that "scoped" cleanup was actually scoped → fixed by giving every file a distinct, non-overlapping email prefix and scoping the session delete to a subquery on that same prefix (`delete from sessions where user_id in (select id from users where email like ...)`) instead of truncating the whole table; next time, grep all test files for shared-resource cleanup patterns before assuming they're isolated, and never issue an unscoped `delete`/`truncate` against a table other test files are using concurrently.
- 2026-10-04 · @fastify/rate-limit route config · registering `@fastify/rate-limit` with `global: false` via `void app.register(rateLimit, { global: false })` and then immediately calling `app.post(..., { config: { rateLimit: {...} } })` on the same instance never actually rate-limited anything (no 429, no `x-ratelimit-*` headers) → the plugin wires itself up via an `onRoute` hook, but that hook is only attached once the plugin's registration callback actually _runs_, which `avvio` defers; the synchronous `app.post()` calls right after `register()` ran before the hook existed, so routes defined that way are invisible to it → fixed by wrapping the rate-limited routes in their own `app.register(async (scope) => { await scope.register(rateLimit, {...}); ...routes on scope... })`, so `await` genuinely blocks route registration until the plugin has booted → whenever a fastify plugin's effect depends on an `onRoute` hook (rate-limit, some auth/ACL plugins), either register it at the very top of `buildApp` before any routes exist, or `await` it inside its own nested `register()` callback — never assume a bare `void app.register(plugin)` followed by synchronous route calls has "happened" yet.
